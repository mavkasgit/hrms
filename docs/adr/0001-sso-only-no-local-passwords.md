# ADR-0001: SSO-only — без локальных паролей

- **Статус:** Принят
- **Дата:** 2026-08-02
- **Связанные задачи:** #33, #34, #35, #36, #37

## Контекст

HRMS исторически поддерживал несколько параллельных механизмов входа: локальный
пароль (self-service установка/смена, админское создание с паролем, invite-ссылки),
Telegram-виджет/бот, OIDC через корпоративный IdP (Authentik) и аварийный
break-glass-вход. Дублирование механизмов приводило к расхождению данных
(роли, профиль, MFA жили и в приложении, и в IdP), увеличивало поверхность
атаки (хранение хэшей, rate-limiting, replay-protection Telegram-подписей)
и усложняло жизненный цикл аккаунтов.

Корпоративный IdP (Authentik) уже покрывает каталог пользователей, группы,
MFA и федерацию. Ведение второй системы идентичности в приложении избыточно.

## Решение

Приложение — **SSO-only relying party**:

1. **Локальных паролей нет.** В БД не хранятся хэши паролей
   (колонки `password_hash` / `password_changed_at` удалены миграцией 047),
   в коде нет хеширования/верификации пользовательских паролей,
   парольный вход (`POST /auth/login`) и self-service смена пароля удалены.
2. **Жизненный цикл аккаунтов — только в Authentik.** Создание, редактирование,
   блокировка и приглашение пользователей выполняются в админке IdP;
   приложение не предоставляет админ-IAM (создание/редактирование/удаление
   пользователей и invite-ссылки удалены).
3. **Локальные записи пользователей создаются JIT** при первом успешном
   OIDC-входе; роли назначает IdP (fail-closed: по умолчанию `viewer`).
4. **Telegram-вход в приложении отсутствует.** Telegram может использоваться
   только как источник входа на стороне Authentik; приложение не хранит
   Telegram-идентификаторы (миграция 046).
5. **Аварийный доступ — break-glass**: единственный непарольный локальный путь,
   проверяется по env-конфигу (`BREAK_GLASS_*`), не по БД; сессии помечаются
   методом `break_glass`.

## Последствия

- Положительные: единая точка управления идентичностью, отсутствие секретов
  пользователей в БД приложения, меньшая поверхность атаки, проще аудит.
- Отрицательные: доступность входа зависит от Authentik (компенсируется
  break-glass); миграция необратима без ручного восстановления данных
  (downgrade миграций 046/047 существует, но хэши паролей не восстанавливаются).
- Ограничения: e2e-логин использует break-glass-форму; dev-режим
  (`DEV_BYPASS_AUTH`) действует только в разработке.

## Реализация

- `#33` — удалён self-service установка/смена локального пароля.
- `#34` — удалена Telegram-подсистема (миграция 046).
- `#35` — удалён админ-IAM пользователей.
- `#36` — удалено парольное хранилище и верификация (миграция 047),
  удалён `POST /auth/login`.
