# ADR-0005: Изоляция тестовых БД — launcher владеет per-run run-DB

Дата: 2026-08-09. Статус: принято.

## Контекст

Раньше конфигурация pytest-БД существовала в двух местах: npm-скрипты
(`test:pytest*`) дёргали общую статичную `hrms_test` на `:5436`, а `conftest.py`
поверх неё сам создавал run-DB `hrms_test_<ts>_<module>_<uuid8>` на каждый
модуль и свипал чужие «устаревшие» БД в session-scoped autouse-фикстуре.
При параллельных агентах это давало флаки: один прогон мог дропнуть БД другого
в момент, когда у той не было активных коннектов (`InvalidCatalogNameError`).
Схема проверена и реализована в ktm2000 (`mavkasgit/ktm2000`,
ADR-0016, коммит `43c24b1`); переносим проверенный код, а не черновик.

## Решение

`npm run test:pytest` — единственная точка входа в backend-тесты.
`scripts/test-run.ps1` (launcher) генерирует `RUN_ID` (12 hex), создаёт
эфемерную БД `hrms_test_<runid>`, выставляет `TEST_RUN_ID` / `TEST_DB_NAME` /
`TEST_DATABASE_URL` (+ alias `HRMS_TEST_DATABASE_URL`), запускает pytest и
в `finally` дропает **только свою** БД. `conftest.py` run-DB не создаёт и не
удаляет — только подключается и изолирует схемы `t_<uuid8>` на модуль.

PostgreSQL-контейнер (`hrms-postgres-pytest`) — **общая инфраструктура**,
живёт независимо от тестового прогона; `docker compose down`/`stop` прогоном
не выполняется. Orphan run-DB (убитый прогон) убирает отдельная команда
`npm run test:db:cleanup` по TTL (24h) через sidecar-таблицу владельцев
`hrms_test_owner` (`created_at`, `last_seen_at`, индекс, ownership-проверка
перед DROP, guard на активные коннекты). Имена БД строго валидируются
`^hrms_test_[0-9a-f]{12}$`. Старые per-module БД (`hrms_test_<ts>_<module>_*`)
вычищаются одноразовой командой `npm run test:db:cleanup-legacy`
(dry-run → `--apply`).

## Почему

Изоляция стала свойством **команды**, а не дисциплиной агента: каждый запуск
сам получает собственную БД и не пересекается с остальными. `conftest.py`
избавлен от владения lifecycle (CREATE/DROP/cleanup ушли).

## Последствия

- При установленном `TEST_DATABASE_URL` имя БД обязано матчить regex launcher'а.
  Ручной serial `pytest` без env работает на статичной `hrms_test`;
  параллельный `pytest -n auto` без launcher — ошибка (fail-fast до xdist).
- CI (GHA): job-контейнер postgres эфемерный, поэтому workflow создаёт run-DB
  сам через `scripts/test-db.py create hrms_test_0c0ffeec0dec` (фиксированный
  id безопасен на свежем контейнере) и дропает её в шаге `if: always()` —
  это сознательное отклонение от «единственная точка входа» launcher'а.
- Тесты изолированы по схемам `t_<uuid8>` на модуль внутри одной run-DB
  (вместо CREATE DATABASE на модуль) — меньше накладных расходов.
- `test:db:cleanup-legacy` — одноразовая уборка старых per-module БД,
  после миграции удаляется.

## Биндинг тестового порта (Windows)

Тестовый PostgreSQL публикуется на обоих loopback-адресах — `127.0.0.1:5436`
и `[::1]:5436`. Причина: asyncpg резолвит `localhost` на `::1` первым, и если
порт опубликован только на IPv4, коннект к `[::1]` виснет ~2с (WSL2-relay
Docker Desktop на Windows) до фолбэка на IPv4. Так как коннект создаётся на
каждый тест (NullPool + per-test фикстура), каждый коннект платил бы 2с —
отсюда почти всё время прогона. С `[::1]`-биндингом коннект мгновенный
(~0.02с). Только loopback: порт не выходит за пределы машины, LAN-экспозиции
нет. После смены биндинга контейнер пересоздаётся (`down` + `up`, готча
`wslrelay.exe` на Windows может держать порт после `stop`).
