# Дополнительная копия бэкапов во внешнее хранилище

## Дата: 2026-10-22
## Тема: backups
## Issue: #126

---

## 1. Задача

Локальный каталог `data/backups` лежит на том же хосте, что и приложение: одна
авария диска уничтожает и прод, и его резервные копии. Нужна вторая, независимая
копия на сетевое или съёмное хранилище — без привязки к ОС, монтирований и задач
планировщика на каждой машине.

## 2. Решение

В образ backend добавлен `rclone` (один статический бинарник). Приложение само
открывает исходящее соединение и пишет архив: контейнеру не нужны bind-mount
сетевого диска, буквы дисков и `net use`. Один и тот же код работает на Windows
и в Linux-контейнере.

- `backend/app/services/backup_retention.py` — общая GFS-политика для локального
  каталога и внешнего хранилища.
- `backend/app/services/backup_remote.py` — разбор адреса, сборка строки
  подключения rclone, копирование с прогрессом, проверка размера, ротация,
  шифрование пароля, статус последней копии.
- `backend/app/api/backups.py` — конфиг и эндпоинты внешней копии.

## 3. Поддерживаемые адреса

| Формат | Пример |
| --- | --- |
| UNC / SMB | `\\nas\backup\hrms` |
| SMB URL | `smb://nas/backup/hrms` |
| SFTP | `sftp://backup-host/backups/hrms` |
| FTP / FTPS | `ftp://backup-host/hrms` |
| WebDAV | `webdav://cloud/remote.php/dav/backup/hrms` |
| NFS (Linux) | `nfs://nas/export/backups/hrms` |
| Локальный / съёмный диск | `D:\Backup\HRMS`, `/mnt/usb/hrms` |
| Готовый remote rclone | `myremote:backup/hrms` |

Режимы доступа: `guest` (без учётной записи) и `credentials` (логин, пароль,
необязательный домен).

## 4. Поведение

- Копия создаётся после успешного локального бэкапа — и при ручном создании,
  и по расписанию планировщика.
- Ошибка копии не ломает бэкап: задача завершается успешно, в `result.remote`
  и в `remote-status.json` фиксируется причина (нет доступа, хост недоступен,
  папка не найдена, rclone не установлен, таймаут).
- После загрузки размер файла на внешнем диске сверяется с локальным.
- Сбой GFS-ротации после успешной загрузки не помечает копию неудачной:
  причина пишется в `rotation_error` статуса, а копия остаётся валидной.
- Ручное копирование существующего бэкапа — `POST /api/backups/{filename}/upload-remote`.
- Копирование выполняется в отдельном потоке (`asyncio.to_thread`), операции
  записи сериализуются `threading.Lock` внутри `backup_remote`.
- Повторы (`--retries`, `--low-level-retries`), общий таймаут
  `BACKUP_REMOTE_TIMEOUT` и ограничение скорости (`--bwlimit`).

## 5. GFS-ротация

Политика общая с локальной: 7 ежедневных, 4 еженедельных, ежемесячные и ручные —
бессрочно. Лимиты внешней копии можно переопределить в UI (`0` — не удалять).
Тип копии читается из JSON-метаданных рядом с архивом (`<filename>.zip.json`).
Локальная и внешняя ротация независимы.

## 6. API

| Метод | Эндпоинт | Назначение |
| --- | --- | --- |
| GET | `/api/backups/config` | Конфиг + блок `remote` без пароля (`has_password`, `last_status`) |
| PATCH | `/api/backups/config` | Обновление `remote`; пароль отсутствует — не менять, пустая строка — очистить |
| POST | `/api/backups/remote/test` | Чтение + запись + удаление пробного файла |
| POST | `/api/backups/{filename}/upload-remote` | Копирование выбранного бэкапа |

## 7. Безопасность

- Пароль хранится в `config.json` зашифрованным (Fernet, ключ из `SECRET_KEY`),
  открытым текстом существует только в момент вызова rclone.
- При смене `SECRET_KEY` расшифровка падает с понятной ошибкой «введите пароль
  заново», а не тихой неудачей копирования.
- Пароль не отдаётся API и не пишется в логи; строки подключения с `pass=`
  вычищаются из сообщений об ошибках (`scrub_secrets`).
- Гостевой доступ небезопасен: любой в сети может читать, изменять и удалять
  копии. UI показывает предупреждение и рекомендует отдельную учётную запись.

## 8. Эксплуатация

- В образе: `COPY --from=rclone/rclone:1.75.2 /usr/local/bin/rclone`.
- Backend без контейнера: задать `RCLONE_PATH` (пусто — искать в `PATH`).
- Конфиг — `data/backups/config.json`, статус — `data/backups/remote-status.json`.
- Новых миграций БД нет.

## 9. Тесты

`backend/tests/test_backup_remote.py`:

- разбор всех поддерживаемых адресов и отказ для неизвестного;
- строка подключения rclone и отсутствие пароля в гостевом режиме;
- шифрование/расшифровка, ошибка после смены `SECRET_KEY`;
- сохранение/очистка/скрытие пароля при обновлении конфига;
- GFS-ротация и пользовательские лимиты;
- проверка адреса: чтение, запись и удаление пробного файла, ошибка удаления;
- сбой ротации не помечает успешно скопированный архив неудачным;
- отказоустойчивость: ошибка внешней копии возвращается статусом `ok: false`,
  а не исключением.

Проверка на реальном NAS/SFTP/WebDAV — вручную (в автотестах rclone не
запускается).
