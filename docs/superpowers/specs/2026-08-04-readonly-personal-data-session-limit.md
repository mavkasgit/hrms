# Spec: Read-only личные данные и лимит сессий (канон user-settings 2.0.0)

## Problem Statement

Сейчас пользователь может редактировать ФИО и email в трёх местах: в приложениях HRMS и KTM-2000 (модуль user-settings, `ProfilePanel`) и в интерфейсе Authentik (`/if/user/#/settings`). Требование — у пользователя не должно быть возможности менять личные данные нигде. Аватар остаётся self-service (пользователь меняет сам). Дополнительно: список сессий в приложениях показывает весь список — нужно показывать только последние 10. И: блок «Способы входа в систему» в разделе «Безопасность» должен давать две кнопки — на дашборд SSO и сразу на настройки входа.

## Solution

ФИО/email становятся read-only для пользователя везде (Authentik + оба приложения). Источник правды — Authentik: данные задаются при invite (как и раньше) и могут корректироваться только администратором IdP. Приложения только читают и кэшируют ФИО/email, не пишут в IdP. Аватар продолжает редактироваться пользователем (bootstrap-push аватара остаётся). `GET /auth/sessions` возвращает `{sessions: [...последние 10], total: N}`.

## User Stories

1. As a пользователь, I want видеть свои ФИО/email в меню профиля, so that я знаю свои данные.
2. As a пользователь, I want чтобы ФИО/email нельзя было изменить нигде (приложения + Authentik), so that личные данные остаются неизменными.
3. As a пользователь, I want иметь понятное сообщение при попытке изменения ФИО/email, so that я понимаю причину отказа.
4. As a пользователь, I want менять свой аватар, so что это единственное self-service поле профиля.
5. As a пользователь, I want видеть только последние 10 сессий с общим количеством, so что список не раздувается.
6. As a пользователь, I want иметь возможность завершить все остальные сессии, so что я могу отозвать невидимые из-за лимита сессии.
7. As an администратор, I want менять ФИО/email через Authentik admin, so что я могу исправить ошибки.
8. As a разработчик, I want единый контракт в обоих приложениях, so что канон не расходится.
9. As a пользователь, I want видеть две кнопки в блоке «Способы входа в систему» (дашборд SSO + настройки входа), so что я могу перейти и в общий каталог приложений, и сразу в настройки единого входа.

## Implementation Decisions

### Порядок раскатки (важно)

1. Authentik (блокировка в IdP) → 2. HRMS-канон (мажор 2.0.0) → 3. KTM-копия. Блокировка в Authentik первой — закрывает «корень»: иначе пользователь обходит блокировку приложений через IdP UI.

### Authentik

- `custom-templates/if/user.html`: скрыть поля ввода name/email в `/if/user/#/settings` (JS-патч shadow DOM, как уже сделано для sources). Аватар и остальные секции остаются.
- `patches/core/api/users.py`: `name`/`email` → read-only в self-service контексте (пользователь не меняет через API), админ с правом `change_user` может править.

### Канон user-settings (HRMS, версия 2.0.0)

- `ProfilePanel`: заменить Input ФИО/email на `ReadonlyBox` (уже есть для username/роли). Аватар/пикер остаются.
- Бэкенд `PATCH /auth/me/profile` (HRMS): ФИО/email → **403** с сообщением; theme/locale принимаются (аватар — через отдельный `PATCH /auth/me/avatar`).
- `unified_profile_service`: убрать bootstrap-push ФИО/email (приложения только читают из IdP); bootstrap-push аватара остаётся (условный push локального seed при пустом удалённом).
- `GET /auth/sessions` → `{sessions: [...10 по last_seen_at DESC], total: N}`.
- `SessionsPanel` + `listSessions()` адаптера: показывают «последние 10 из N»; кнопка «завершить все остальные» (`DELETE /auth/sessions/others`) остаётся.
- `refresh=1`: только после смены аватара; открытие меню без форса (TTL 300с не трогаем).
- Обновить манифест канона: версия 2.0.0 (мажор — ломающий контракт `GET /auth/sessions`), `sync`.

### Блок «Способы входа в систему» (SecurityPanel)

В разделе «Безопасность» блок «Способы входа в систему» (Единый вход SSO) получает **две кнопки** вместо одной:

1. **«Дашборд SSO»** — ведёт на дашборд Authentik (`{public_base_url}/if/user/`).
2. **«Открыть настройки входа»** — ведёт сразу на страницу настроек Authentik (`{public_base_url}/if/user/#/settings`, например `http://192.168.100.200:9000/if/user/#/settings`).

Реализация (в каноне, копируется в оба приложения):

- `IdpLinks` (types.ts) расширяется вторым полем: `sso_dashboard_url: string | null` рядом с существующим `user_settings_url`.
- Бэкенд `idp_links_data()` (в `authentik_admin_service.py`/`authentik_client` — канонный модуль) возвращает оба URL:
  - `user_settings_url` = `{base}/if/user/#/settings` (настройки входа — таргет второй кнопки);
  - `sso_dashboard_url` = `{base}/if/user/` (дашборд SSO — таргет первой кнопки).
- `SecurityPanel` рендерит две кнопки в карточке SSO, обе открывают в новой вкладке (`window.open(..., "_blank", "noopener,noreferrer")`).
- i18n: добавляется строка для первой кнопки (`security.idpDashboard` / аналог), строка `idpOpen` («Открыть настройки входа») переиспользуется для второй.
- Блок «Способы входа в систему» с двумя кнопками входит в ядро канона и хешируется в манифесте.

### KTM-копия

- Скопировать канон 2.0.0 (манифест → KTM, версия 2.0.0).
- Те же изменения бэкенда KTM: 403 на ФИО/email, `{sessions, total}`, убрать bootstrap-push ФИО/email.

## Testing Decisions

- **Backend**: 403 при попытке изменить ФИО/email через `PATCH /auth/me/profile`; theme/locale принимаются; `GET /auth/sessions` возвращает максимум 10 и корректный `total`; bootstrap-push ФИО/email удалён (аватар остаётся). Prior art: `test_unified_profile.py`, `test_sessions_api.py`, `test_me_ttl.py`, `test_me_links_events.py`.
- **Frontend**: `UserSettingsDialog.test.tsx` — `ProfilePanel` показывает read-only ФИО/email, `SessionsPanel` показывает «последние 10 из N», avatar picker доступен; `SecurityPanel` показывает две кнопки («Дашборд SSO» и «Открыть настройки входа») с корректными URL.
- Обновить существующие тесты, сломанные контрактом `{sessions, total}`, read-only профилем и новым полем `sso_dashboard_url` в `IdpLinks`.
- Ручной smoke: ФИО/email нельзя изменить ни в HRMS, ни в KTM, ни в Authentik; смена аватара работает и синкается; список сессий показывает 10 + total; обе кнопки в «Способы входа в систему» ведут на правильные страницы Authentik.

## Out of Scope

- Ограничение сессий в интерфейсе Authentik (там свои SSO-сессии IdP, не трогаем).
- Блокировка темы/языка (это предпочтения, остаются self-service).
- Автоматический синк ФИО/email из внешних источников (Google/Telegram) — не добавляем, это перезаписало бы админские данные.
- Пагинация сессий (страницы) — только лимит 10 + total.
