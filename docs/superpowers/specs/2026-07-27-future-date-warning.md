# Spec: Мягкое предупреждение для будущей даты приказа

## Problem Statement

При создании приказа с датой в будущем система возвращает жёсткую ошибку 422 ("Дата приказа не может быть в будущем"). Это мешает легитимным сценариям — например, приказ на отпуск или вызов из отпуска, которые издаются заранее. При этом фронтенд никак не подсказывает пользователю о проблеме: он выбирает дату, отправляет форму и получает неочевидную ошибку.

## Solution

Заменить жёсткий запрет на мягкое предупреждение. Пользователь видит информационное сообщение при выборе будущей даты, но может свободно отправить форму. Бэкенд принимает любую дату без ограничений.

## User Stories

1. As an HR-оператор, I want видеть предупреждение при выборе будущей даты приказа, so that я могу заметить опечатку до отправки формы.
2. As an HR-оператор, I want иметь возможность создать приказ с будущей датой, so that я могу оформить приказ на отпуск заранее.
3. As an HR-оператор, I want чтобы предупреждение не блокировало отправку формы, so that мне не нужно делать лишних кликов для подтверждения.
4. As an HR-оператор, I want видеть одинаковое предупреждение во всех формах приказов, so that поведение системы предсказуемо.
5. As an HR-оператор, I want видеть предупреждение при редактировании даты существующего приказа, so that я защищён от опечаток и при редактировании.
6. As an HR-оператор, I want видеть предупреждение в групповых формах приказов, so that защита от опечаток работает везде.
7. As a разработчик, I want использовать единый компонент DocumentDatePicker во всех формах, so that логика предупреждения не дублируется.
8. As a разработчик, I want чтобы бэкенд не отклонял будущие даты, so that фронтенд — единственная точка контроля UX.

## Implementation Decisions

- Новый компонент `DocumentDatePicker` в слое shared/ui. Инкапсулирует DatePicker + пассивный жёлтый алерт с текстом "Дата указана в будущем".
- Компонент принимает тот же props-интерфейс что и существующий DatePicker, плюс рендерит предупреждение когда выбранная дата > сегодня.
- Предупреждение пассивное: не блокирует отправку, не требует подтверждения, не содержит чекбокс.
- Порог: любая дата строго больше сегодняшнего дня.
- Единообразно для всех типов приказов — без исключений по типу (отпуск, приём, увольнение и т.д.).
- Замена `<DatePicker>` на `<DocumentDatePicker>` во всех формах создания и редактирования приказов: индивидуальные, групповые, отпускные страницы.
- Бэкенд: валидатор `order_date_not_future` удаляется из схемы `OrderCreate` полностью. Никаких логов, флагов, конфигов.
- Схемы `GroupOrderCreate`, `VacationUnpaidGroupOrderCreate`, `WeekendCallGroupOrderCreate`, `OrderUpdate` не изменяются (у них и так нет валидатора).

## Testing Decisions

- Хороший тест проверяет внешнее поведение компонента/API, а не внутреннюю реализацию.
- **Frontend**: компонентный тест `DocumentDatePicker` (Vitest + Testing Library + jsdom). Проверяет: предупреждение видимо при будущей дате, не видимо при прошедшей/сегодняшней. Prior art: `UserSettingsDialog.test.tsx`.
- **Backend**: тест в стиле `test_general_order_creation.py` — создание приказа с будущей датой возвращает успех (не 422). Prior art: `test_general_order_creation.py`, async pytest.
- E2E Playwright тесты не требуются.

## Out of Scope

- Изменение DatePicker для форм, не связанных с приказами/документами.
- Добавление предупреждений для других полей (не дата).
- Аудит-логирование приказов с будущей датой.
- Конфигурируемость порога или текста предупреждения.
- Миграция существующих данных.

## Further Notes

- В кодовой базе 10+ фронтенд-форм создают приказы. Все используют draft-then-commit паттерн через OnlyOffice. Замена DatePicker на DocumentDatePicker — механическая, по одной строке на форму.
- Фронтенд сейчас не имеет тестов в shared/ui — этот тест будет первым. Использовать прагму `// @vitest-environment jsdom`.
